# Proteus 1.0.0 development notes — unreleased

These notes describe the intended 1.0 release scope implemented on the development
line. They are not a release announcement or evidence that release acceptance has
completed. Package metadata remains `0.4.0` until the release procedure changes it.

## Framework and methods

- Versioned recipes, plugin registration, typed contracts, immutable manifests
  and dependency/source locks separate methods, actors, subjects and evaluation.
- GEPA, ACE, Meta-Harness, Combee-ACE/GEPA and single-space CORAL have bounded
  integration profiles, offline examples and original-domain preparation entries.
  Their reference revisions and deviations remain explicit. See the
  [method support matrix](../V1_OVERVIEW.md#included-method-profiles).
- Shared services provide immutable candidates and lineage, task/state protocols,
  eligible-score archives and search policies, budgeted parallel workflows,
  Combee aggregation and dynamic batch control.
- Persistent workers, formal evaluation submission, versioned shared knowledge,
  session continuation and event interventions support asynchronous research.
- Pinned Harbor/Docker execution verifies candidate/image identity, independent
  private grading, source builds, worker boundaries and cleanup.

## Researcher workflow

The catalog, five plugin templates and proposed `proteus.api.v1` import surface
support external extensions. Tutorials demonstrate self-evaluation evidence,
configuration-only final selection, and a separate parent-selection experiment.
Saved-run export provides task/cohort tables, candidate lineage, role/stage costs,
attempts and controller timing. StudySpec validates declared conditions and seeds,
preserving missing scores/costs/time. Domain reports retain additional original
task regrading and cooperation evidence.

## Compatibility

The existing native CLI, evolution protocol, source activation/repair semantics,
goals, feedback visibility, surface measurements and adapter interfaces remain.
Native recipes use that transaction engine; they do not retroactively gain managed
usage coverage. Final adapter inputs are retained at their observable boundary;
opaque harness-internal provider requests can remain unavailable.

Existing runs are not rewritten or automatically migrated. Changed source,
dependencies, configuration or incompatible plugin state require the original
environment or a new experiment. The versioned API is proposed for 1.0, not a
stability promise for every internal class. Read [compatibility rules](../V1_COMPATIBILITY.md)
before upgrading an unfinished run.

## Outstanding release acceptance

All five families still need the real-model results required by the
[implementation plan](../plans/proteus-1.0.0-implementation-plan.md), including
complete declared task splits, baselines, seeds, budgets and deviations. Combee
needs quality/cost/time evidence; CORAL needs single/multi-worker evidence and
sharing analysis. Fixtures and successful container launches do not satisfy this.

Native aggregate usage coverage and the remaining infrastructure acceptance must
also be resolved. The selected release commit must pass full CI, installed
distribution/optional-dependency checks, Harbor and live runtime smoke. Feature
integration, final main review, version/tag and publication remain separate gates
under [RELEASING.md](../RELEASING.md). No required live gate may silently skip.
