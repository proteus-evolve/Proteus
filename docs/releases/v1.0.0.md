# Proteus 1.0.0 development notes — unreleased

These notes describe the intended 1.0 release scope implemented on the development
line. They are not a release announcement or evidence that release acceptance has
completed. Package metadata remains `0.4.0` until the release procedure changes it.

## Framework and methods

- Versioned recipes, plugin registration, typed contracts, immutable manifests
  and dependency/source locks separate methods, actors, subjects and evaluation.
- GEPA, ACE, Meta-Harness, Combee-ACE/GEPA and single-space CORAL have bounded
  integration profiles, offline examples and original-domain preparation entries.
  Their reference revisions and deviations remain explicit. See the
  [method support matrix](../V1_OVERVIEW.md#included-method-profiles).
- Shared services provide immutable candidates and lineage, task/state protocols,
  eligible-score archives and search policies, budgeted parallel workflows,
  Combee aggregation and dynamic batch control.
- Persistent workers, formal evaluation submission, versioned shared knowledge,
  session continuation and event interventions support asynchronous research.
- Source-bound harness integrations expose declared actor, subject, coding-workspace
  and evolution roles. Minimal, LLM, Pi, DSH and Codex have different capabilities;
  Aki retains its legacy CLI scope. Representation-compatible runners/projections
  are required. Sixteen bounded live pilot cells do not establish every method/role
  combination or native-session multiworker behavior. See the
  [actual support matrix](../V1_HARNESS_ROLES.md#capability-and-evidence-matrix).
- Pinned Harbor/Docker execution verifies candidate/image identity, independent
  private grading, source builds, worker boundaries and cleanup.

## Researcher workflow

The catalog, five plugin templates and proposed `proteus.api.v1` import surface
support external extensions. Tutorials demonstrate self-evaluation evidence,
configuration-only final selection, and a separate parent-selection experiment.
Saved-run export provides task/cohort tables, candidate lineage, role/stage costs,
attempts and controller timing. StudySpec validates declared conditions and seeds,
preserving missing scores/costs/time. Domain reports retain additional original
task regrading and cooperation evidence.

## Compatibility

The release-preparation fixes retain reservations for uncertain dispatched work,
make Native checkpoint publication recoverable, and bound Docker cleanup with a
private reconciliation marker. Shared snapshot objects and transactional ledger
totals reduce repeated persistence work. Schema upper bounds and paired study
seed mappings are now enforced. DSH exposes model selection ownership while
preserving its legacy default. The unused `EpisodeSpec.extra_env` field is removed;
unsupported configuration fails instead of being ignored. See the
[review closure and scale limits](../V1_RELEASE_ACCEPTANCE.md).

The existing native CLI, evolution protocol, source activation/repair semantics,
goals, feedback visibility, surface measurements and adapter interfaces remain.
Native recipes use that transaction engine; they do not retroactively gain managed
usage coverage. Final adapter inputs are retained at their observable boundary;
opaque harness-internal provider requests can remain unavailable.

The separate common Native evolution profile uses last-valid activation without
outer score selection; its goal text is separate from external grading. The common
harness subject currently runs independent serial trials. Parallel after-prediction
model grading requires the grader's parallel capability and respects its concurrency
cap; recovered parallel results verify private grader provenance before joining.

Existing runs are not rewritten or automatically migrated. Changed source,
dependencies, configuration or incompatible plugin state require the original
environment or a new experiment. The versioned API is proposed for 1.0, not a
stability promise for every internal class. Read [compatibility rules](../V1_COMPATIBILITY.md)
before upgrading an unfinished run.

## Outstanding release acceptance

The [frozen October study](../../recipes/README.md) now archives 15 adapted
single-seed profiles and their real-model results. Their historical cores and
custom runtime patches are mapped to [current implementation evidence](../V1_EXPERIMENT_ACCEPTANCE.md).
This does not establish matched paper reproduction or complete the research
acceptance in the [implementation plan](../plans/proteus-1.0.0-implementation-plan.md).
The [acceptance disposition](../V1_RELEASE_EVIDENCE_MAP.md) records completed
historical GEPA/AIME and ACE/Formula full-split results. Meta-Harness's historical
JSON proposer and current bounded coding-proposer pilots are different protocols;
current coding-search benchmark acceptance is still pending. Combee's four online
conditions have a complete historical quality/API-upper/study-elapsed observation
table; offline continuous timing remains unknown. Fixed-trace and declared-comparison
acceptance still need review. Shared-host and cross-runtime observations do not
establish isolated speedup, but positive speedup is not an added acceptance gate.
CORAL's one/two-worker runs, own feedback and
pause/fresh-fallback generations are real evidence; actual cross-worker prompt use,
applied interventions and interrupted recovery still need source-bound closure.
Neither a cooperation benefit nor multi-seed significance is established. Deferring
mandatory plan items requires an explicit scope decision, not an experimental label.

Unknown native usage remains unknown, with unsupported finite caps rejected and
uncertain dispatch reservations retained. Final infrastructure acceptance is still
required: the selected release commit must pass full CI, installed
distribution/optional-dependency checks, Harbor, Native source integration and full
live runtime smoke. Feature
integration, final main review, version/tag and publication remain separate gates
under [RELEASING.md](../RELEASING.md). No required live gate may silently skip.
